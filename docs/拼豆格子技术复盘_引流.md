# 做了个拼豆/像素画小程序：把微信内容安全机审和渲染引擎啃下来了

## 缘起

想把一张喜欢的图变成能照着拼的拼豆（Perler beads）/ 像素画模板，市面上的工具要么要会员、要么色号对不上、要么大图直接崩。于是自己动手做了一个微信小程序：**拼豆格子（PinDou Grids）**——选一张图，自动生成行列标号、色号对照表、材料清单，还能导出高清制作图。纯原生框架，没用任何第三方渲染库。

> 开源地址：https://github.com/345761556/pin-dou-master

做的过程中踩了不少坑，尤其是**内容安全**和**大图渲染**这两块。下面把设计决策摊开讲，给同样在做小程序、或在和微信机审较劲的同学参考。

## 一、内容安全：为什么必须是 fail-closed

做小程序绕不开内容安全。用户上传的图片得过微信 `security.mediaCheckAsync` 机审。这里最大的坑**不是"怎么调 API"**，而是：**审核结果没回来之前，这张图到底放不放行？**

很多实现是"先放行、出事再删"，这在合规上是有风险的。我们的设计是 **fail-closed（默认拒绝）**：检测链路任何环节没完成——超时、限频、通道不可用、图片过大——一律**默认拦截**；只有开发版（develop）本地调试才回退放行，体验版 / 正式版强制拦截。

完整链路：

- 前端选图即校验（文件类型、大小 ≤10MB、宽高 ≤6000px、真实格式基于文件内容而非扩展名）→ 压缩到 ≤800px → 云存储中转
- `secCheck` 云函数调微信 `mediaCheckAsync`（异步）→ 微信通过 `wxa_media_check` 消息推送结果 → `mediaCheckResult` 云函数写入 `sec_check_results`
- 前端以 1s 间隔轮询读取 `suggest`（pass 放行 / review、risky 拦截）

三个关键决策：

1. **超时兜底，绝不悬挂**。提交后最多轮询 20 次（约 20s），若微信推送没到（网络抖动 / 推送丢失 / 没配回调），按 fail-closed 拦截并提示「内容安全检测暂不可用，请稍后重试」。检测结果**永远不会处于悬挂状态**——超时即拒绝，绝不"先放再说"。
2. **误杀救济要清晰**。拦截时按原因区分提示（违规 / 图片过大 / 操作频繁 / 服务不可用），用户可直接换图重试，本地相册原图不受影响。因为微信内容安全 API **不提供人工申诉通道**，误判的唯一救济就是换图，所以把交互设计成"明确拒绝 + 可重试"比"无限等待"体验更可控。
3. **隐私不留痕**。检测图片存于云存储 `sec_check/` 目录，检测结束云函数立即删除；`sec_check_results` 只留 `suggest` / `label` / `errcode` / 时间戳，不含图片本体。

## 二、渲染引擎：大图不崩、不卡

拼豆本质是用 30–50 个有限色卡去逼近原图。渲染引擎 `beadEngine.js` 的几个决策，都是被真机 OOM 和"无响应"警告逼出来的：

- **规模硬上限**。模板格子数最多 8000（行列乘积统一钳制）。一张 400×400 的图也会被钳到 ≤8000 格，绝不做 16 万格全量计算。
- **降采样**。颜色量化采样最多 5000 像素，避免中位切分（median cut）对超大图全量计算；前端生成前再压缩到 ≤800px 边长，双保险降 canvas 内存。
- **分块让出主线程**。生成按 `行数/24` 分块，每块完成后 `await setTimeout(0)` 让出主线程一个 macrotask，避免长时间阻塞触发"无响应"警告；Floyd-Steinberg 抖动分支在**整行处理完**后才让出，保证行序正确。
- **导出内存预算**。导出候选从 50px 一路降级到 8px，估算位图字节（宽×高×4）超 33MB 直接跳过，避开低端机尝试 50MB+ 大位图导致 WebView 崩溃。
- **存储瘦身**。网格矩阵用 RLE 压缩编码替代完整二维数组，单条历史记录体积大幅下降；历史最多 50 条，超限挤出最旧并同步清理对原图。

## 三、限频：用原子条件更新防 TOCTOU

`secCheck` 云函数按 openid 每小时 100 次限频。最容易写错的地方是"先读计数、再判断、再写回"——这在并发下会有 **TOCTOU 竞态**，限频会被击穿。

正确做法是用数据库的**原子条件更新**：`_.inc` 自增配合 `_.lt` 上限条件，一次操作完成"判断是否超限 + 计数 +1"，不存在中间窗口。数据库故障时降级到单实例内存兜底并告警，不会直接放行。

## 收尾

这个项目从踩坑到跑稳，最大的体会是：小程序的"健壮性"不在功能多，而在**失败路径都想清楚**——检测失败怎么拦、大图怎么降级、并发怎么限、存储满了怎么挤。把这些边界写进代码和测试，比堆功能值钱。
